# 历史订单累积后，安卓端订单操作变慢

## 现场现象

2026-10-15 用户反馈：后端与 PostgreSQL 运行于麒麟 710 平板的 Termux，通常有 2 台、偶尔 3 台安卓设备连接。每天约产生 130 单，约 4 天后（约 520 单），实际使用设备上点击“肉”“主食”“出餐”变慢。其他设备同步未感到明显延迟。应用内清空订单后改善。

这里的“实际使用设备”指门店运行安卓应用的设备。本文命令行结果来自开发电脑，不能当作麒麟 710 或门店设备的实测延迟。

## 排查结论与证据

当前最明确的性能缺陷在前端工作台的派生计算：

1. `orderRepository.list('all')` 每页获取 200 单，并持续读完全部历史订单；连接建立、重连后的快照仍会读全量。
2. 点击步骤或出餐按钮先执行本地乐观更新。`ordersById` 的引用改变后，`OrderList` 和 `OrderControls` 都重新遍历全部历史订单，筛选当天订单、计算计数。
3. 原日期判断每单都将订单时间和当前时间分别转换到 `Asia/Shanghai`。两轮遍历合计约 `4 × 历史订单总数` 次时区转换；520 单约 2080 次。服务器确认后的状态更新可能再次触发计算。
4. 已有虚拟列表限制实际渲染的行数，但无法减少渲染之前的全量日期筛选。

后端 `ToggleStep` / `ToggleServed` 通过订单 ID 查询、更新单条订单，在事务提交后广播变化，没有在该提交链路逐单遍历历史订单。现有证据不足以认定后端硬件是主要原因，也不能仅凭清空后改善认定 PostgreSQL 变慢：清空同时减少了每台客户端的数据与计算量。

这仍不是门店设备上的端到端性能诊断。网络、数据库提交、Android 后台限制及设备负载，如仍有症状，应结合现场日志与客户端时间线继续区分。

## 基准方法

基准必须直接调用生产环境使用的工作台筛选与计数函数，以及独立实例中的真实订单 store。提取函数时先保持原有逻辑，记录基线后再优化，避免用两套手写实现做比较。

- 固定模拟订单，每天 130 单，分别保留 1 天、4 天、14 天数据（130 / 520 / 1820 单），当天均为 130 单。
- 模拟主食、肉、出餐操作的本地乐观更新和服务器确认后的本地重算。
- 每组保留 **5 次测量**，使用**算术平均值**。命令行按顺序启动 5 个独立 Node 进程；应用内在同一 WebView 进程中顺序运行 5 轮，每轮新建隔离 store。两种运行环境需分别比较。
- 每轮每项操作先预热 2 次，再测量 5 次，得到该轮每次操作的平均耗时；最终对 5 轮均值再取算术平均。所有轮次权重一致，不丢弃慢样本，不使用中位数。
- 保存五次原始数据、平均值、运行环境、代码版本与测量范围，前后使用同一基准配置。
- 只测本地同步计算，不包含 HTTP、WebSocket、数据库、React DOM 提交与屏幕绘制；模拟确认不代表真实服务器响应耗时。
- 应用内入口使用隔离的模拟订单和内存存储，不改变门店真实订单或筛选设置。

```sh
pnpm benchmark:orders --label baseline --output benchmarks/order-workspace/results/baseline.json
pnpm benchmark:orders --label fixed --output benchmarks/order-workspace/results/fixed.json --compare benchmarks/order-workspace/results/baseline.json
```

每个结果 JSON 保留五轮原始值和分阶段均值。命令行比较会拒绝不一致的基准协议、CPU 或 Node 版本。不要与测试、构建或另一轮基准并行运行。详细说明见 [benchmark README](../benchmarks/order-workspace/README.md)。

### 优化前基线

已在提交 `e314fee` 上顺序完成 5 个独立进程的基线，原始结果见 [baseline.json](../benchmarks/order-workspace/results/baseline.json)。每项数值均为五轮算术平均，每次操作合计包含本地乐观更新与模拟服务器确认后的两次工作台重算。

| 历史总单量（今日均 130 单） | 肉（ms） | 主食（ms） | 出餐（ms） |
| --- | ---: | ---: | ---: |
| 130 | 65.290 | 62.857 | 62.491 |
| 520 | 260.203 | 260.243 | 258.612 |
| 1820 | 922.824 | 905.477 | 915.016 |

该基线复现了数据增长带来的本地同步计算开销；不是门店设备的实测。

### 修复后五次平均与前后对比

修复后测量对应提交 `5fed99e`，结果见 [fixed.json](../benchmarks/order-workspace/results/fixed.json)，其中也包含自动生成的降幅和加速比。两份结果的基准协议完全一致，均为五次算术平均，并已独立从原始试验值重新计算核对。

| 历史总单量（今日均 130 单） | 肉：前 → 后（ms） | 主食：前 → 后（ms） | 出餐：前 → 后（ms） |
| --- | ---: | ---: | ---: |
| 130 | 65.290 → 1.276 | 62.857 → 0.980 | 62.491 → 1.100 |
| 520 | 260.203 → 1.999 | 260.243 → 1.929 | 258.612 → 1.828 |
| 1820 | 922.824 → 4.966 | 905.477 → 4.906 | 915.016 → 4.977 |

520 单时，模拟操作的同步计算总耗时减少约 99.2%～99.3%。以“肉”为例，本地乐观更新后的视图重算从 128.163 ms 降为 0.897 ms，模拟确认后的视图重算从 130.688 ms 降为 0.922 ms。数字不代表整次点击、网络往返或真实设备的响应时间。

测量环境：Linux x64，AMD Ryzen 7 5800H（16 逻辑 CPU），Node v24.18.0，V8 13.6.233.17-node.50；dayjs 1.11.21、Zustand 5.0.14、Vite 8.2.1，进程时区固定为 UTC。没有并行运行测试或构建。

本机已有 pnpm 12.6.0，而仓库环境说明要求 pnpm 11。尝试使用 Corepack 获取 11 时，registry.npmjs.org 的 TLS 连接失败。此次前后测量和验证均使用现有 pnpm，没有改动依赖版本或锁文件；报告如实保留启动器版本，不能声称已在 pnpm 11 下验证。

基线包含完整的设置页入口，可从 `e314fee` 构建优化前版本；`a8d41d5` 包含优化实现。门店比较应在同一台实际设备上使用两种实现分别运行五轮，保持相同测试协议及相近的前台负载，不将开发电脑的绝对毫秒数套用到安卓设备。


## 修复范围

实现已改为：

- 每轮筛选或计数只用 dayjs / `Asia/Shanghai` 计算一次业务日的 `[startAt, endAt)` 范围；逐单解析时间戳并做数值比较，不再逐单转换时区。
- 分别解析当天开始和结束，而非固定加 24 小时，保留上海历史夏令时日期的正确边界。
- 使用稳定的业务日状态作为组件 memo 依赖，上海午夜、页面重新可见、窗口恢复焦点和 pageshow 时刷新，避免跨日后沿用昨日结果。
- 保持筛选顺序、按完成时间倒序、计数、服务器版本和乐观更新语义；排除无效订单时间。没有增加持久缓存，也没有改变订单模型。

仍会遍历内存中的历史订单，复杂度仍为 O(N)，但逐单计算已大幅降低。历史快照下载、内存占用及更大规模的 store 排序开销仍存在，不能据此声称无限历史数据都没有成本。

本次保留历史订单和现有同步协议。历史数据按需加载属于后续优化；不以自动删除订单作为性能修复。

## 验证

- `pnpm test`：70 个测试文件、501 项测试全部通过，包含新增页面的 Chromium 交互与无障碍检查。
- `pnpm lint`：通过；保留原有 `NowContext.tsx` 的一条 Fast Refresh 警告，未修改无关组件。
- `pnpm build`：类型检查及生产构建通过；仍有原有主包体积提示。基准页面按路由懒加载。
- 回归覆盖上海午夜的包含/排除边界、不同时区表示、无效日期、历史夏令时（包括 UTC 主机时区）、排序、状态更新后计数，以及日期定时刷新和恢复前台后的校正。测试也检查时区转换调用量不会随历史订单增加。
- 命令行 JSON 的五轮均值已经从原始值独立重新计算；前后使用相同测量协议。
- 在独立 Chromium 中以 1440 px 桌面及 390 px 手机宽度执行真实的应用内五轮模拟测试，核对三种规模及平均值，展开原始数据、复制结果、重新运行和取消均通过，无横向溢出或页面异常。此为开发电脑浏览器验证，不是安卓真机测试。

## 门店复测

进入 **设置 → 订单基准测试 → 测试订单处理性能 → 开始测试 5 轮**，在实际安卓设备上重复运行相同的模拟场景并复制结果；没有剪贴板权限时，可长按完整 JSON 手动复制。运行中支持取消，离开页面或切到后台会停止，取消不会生成不完整的平均值。订单快照同步失败时，仍可进入该本地测试页。

它测量的是运行应用设备的本地处理能力，不能单独判断后端或网络是否慢。建议在设备空闲、应用前台时测试，并连同应用版本、设备信息和实时连接诊断结果一起记录。应用内 JSON 在原生环境下包含版本号与构建号；网页环境无原生版本信息时使用空值。
