# 历史订单累积后，安卓端订单操作变慢

## 现场现象

2026-10-15 用户反馈：后端与 PostgreSQL 运行于麒麟 710 平板的 Termux，通常有 2 台、偶尔 3 台安卓设备连接。每天约产生 130 单，约 4 天后（约 520 单），实际使用设备上点击“肉”“主食”“出餐”变慢。其他设备同步未感到明显延迟。应用内清空订单后改善。

这里的“实际使用设备”指门店运行安卓应用的设备。本文命令行结果来自开发电脑，不能当作麒麟 710 或门店设备的实测延迟。

## 排查结论与证据

当前最明确的性能缺陷在前端工作台的派生计算：

1. `orderRepository.list('all')` 每页获取 200 单，并持续读完全部历史订单；连接建立、重连后的快照仍会读全量。
2. 点击步骤或出餐按钮先执行本地乐观更新。`ordersById` 的引用改变后，`OrderList` 和 `OrderControls` 都重新遍历全部历史订单，筛选当天订单、计算计数。
3. 原日期判断每单都将订单时间和当前时间分别转换到 `Asia/Shanghai`。两轮遍历合计约 `4 × 历史订单总数` 次时区转换；520 单约 2080 次。服务器确认后的状态更新可能再次触发计算。
4. 已有虚拟列表限制实际渲染的行数，但无法减少渲染之前的全量日期筛选。

后端 `ToggleStep` / `ToggleServed` 通过订单 ID 查询、更新单条订单，在事务提交后广播变化，没有在该提交链路逐单遍历历史订单。现有证据不足以认定后端硬件是主要原因，也不能仅凭清空后改善认定 PostgreSQL 变慢：清空同时减少了每台客户端的数据与计算量。

这仍不是门店设备上的端到端性能诊断。网络、数据库提交、Android 后台限制及设备负载，如仍有症状，应结合现场日志与客户端时间线继续区分。

## 基准方法

基准必须直接调用生产环境使用的工作台筛选与计数函数，以及独立实例中的真实订单 store。提取函数时先保持原有逻辑，记录基线后再优化，避免用两套手写实现做比较。

- 固定模拟订单，每天 130 单，分别保留 1 天、4 天、14 天数据（130 / 520 / 1820 单），当天均为 130 单。
- 模拟主食、肉、出餐操作的本地乐观更新和服务器确认后的本地重算。
- 每组保留 **5 次独立测量**，使用**算术平均值**；预热和单次测量内部重复次数由基准元数据记录。
- 保存五次原始数据、平均值、运行环境、代码版本与测量范围，前后使用同一基准配置。
- 只测本地同步计算，不包含 HTTP、WebSocket、数据库、React DOM 提交与屏幕绘制；模拟确认不代表真实服务器响应耗时。
- 应用内入口使用隔离的模拟订单和内存存储，不改变门店真实订单或筛选设置。

命令、结果和对比在基准完成后补充。

## 修复范围

优先消除每次操作对历史订单重复做时区转换的开销，保持上海业务日期、筛选、完成时间排序和计数语义。跨午夜及应用恢复前台时应重新判断当天。

本次保留历史订单和现有同步协议。历史数据按需加载属于后续优化；不以自动删除订单作为性能修复。

## 门店复测

设置中的“订单性能基准”用于在实际安卓设备上重复运行相同的模拟场景，并复制结果。它测量的是运行应用设备的本地处理能力，不能单独判断后端或网络是否慢。建议在设备空闲、应用前台时测试，并连同应用版本、设备信息和实时连接诊断结果一起记录。
