# 订单工作台后续性能优化规划

编制日期：2026-10-15  
文档状态：待实施规划

## 1. 背景与目标

已发布的性能修复通过预先计算上海业务日期的时间范围，消除了订单状态更新过程中逐单重复进行时区转换的主要开销。问题分析、既有基准方法及修复结果见[历史订单性能问题记录](order-toggle-performance.md)。

当前实现仍会在客户端保存全部历史订单，并在订单变化后执行对象复制、当日订单筛选和计数等操作。因此，单次处理成本虽已明显下降，仍会随历史订单总量增加。

后续优化的总体目标是：在保留完整历史数据及现有业务语义的前提下，使日常订单操作的客户端处理成本主要取决于当前营业日的订单规模，降低历史数据累积对交互、同步恢复和内存占用的影响。

本文件规定后续优化方向、实施顺序、依赖关系和验收要求，不表示相关优化已经完成，也不将开发电脑基准结果视为门店安卓设备的实际响应时间。

基准覆盖面、真实交互测量、长期运行测试及门店诊断能力的扩展，按照[性能基准测试与现场诊断扩展实施方案](performance-benchmark-expansion-plan.md)执行。相关测量应先于对应生产优化建立基线。

门店照片中的观测结果已单独归档于[门店订单基准测试观测记录](order-benchmark-onsite-2026-10-15.md)：当日固定 130 单时，三种操作在 520 单总量下为 6.46～6.88 毫秒，在 1820 单下为 15.90～16.14 毫秒，支持继续降低历史累积带来的客户端处理成本。由于未取得五轮明细及环境信息，该照片尚不能作为可复算的正式基线，也不能据此识别具体热点或评价后端性能。

## 2. 现状与约束

| 环节 | 当前实现 | 主要成本或限制 |
| --- | --- | --- |
| 快照加载 | 按每页 200 单连续获取全部历史订单；连接建立或恢复后重新获取快照 | 请求数量、传输量、解析时间和内存占用随历史总量增长 |
| 状态存储 | 更新订单时复制 `ordersById` 对象 | 对象复制成本仍与客户端保存的订单数量相关 |
| 实时更新 | 通过批量更新方法合并已接受的订单，再重新生成完整排序 ID 数组 | 普通进度变化也可能触发不必要的全量排序和数组分配 |
| 工作台视图 | 列表筛选和顶部计数分别遍历订单集合 | 存在重复派生计算；任一已接受更新均可能触发重新计算 |
| 现有基准 | 模拟单笔乐观更新及单笔确认后的本地计算 | 尚未单独覆盖实时批量更新、初次加载和重连恢复路径 |

现状依据为[订单加载实现](../src/services/orderRepository.ts)、[订单状态存储实现](../src/store/order.ts)、[工作台派生计算](../src/services/orderWorkspaceView.ts)及[基准工作负载](../src/services/orderBenchmark.ts)。

实时事件中的同版本或旧版本记录会被现有版本检查忽略。仅当新版本记录被接受并进入批量更新方法时，才发生上述排序开销。本机操作的 HTTP 确认与 WebSocket 事件到达顺序也会影响实际执行路径。

列表已采用虚拟化，订单卡片按 ID 订阅数据。因此，当前问题不能表述为“所有历史订单卡片均会重新渲染”；需要优化的是数据处理、派生计算以及由集合引用变化引起的更新。

实施过程中应持续满足以下约束：

- 历史订单继续保存在服务端，不以自动删除业务数据作为性能优化措施。
- 保留订单时间线顺序、已完成订单排序、筛选和计数语义。
- 保留服务端版本校验、乐观更新、失败回滚及实时事件去重机制。
- 业务日期统一按 `Asia/Shanghai` 解释，明确处理切日及应用恢复前台的边界。
- 测试与诊断使用隔离数据，不改变门店真实订单。

## 3. 实施顺序

| 阶段 | 工作内容 | 预期收益 | 依赖与实施判断 |
| --- | --- | --- | --- |
| 第一阶段 | 补充实时更新基准，并消除批量更新中的无效排序 | 降低常见实时状态更新的处理成本，改动范围较小 | 可先在前端独立实施；先记录基线，再修改实现 |
| 第二阶段 | 将工作台数据范围限制为当前营业日所需订单，历史订单按需查询 | 同时降低请求、内存、对象复制和遍历成本，减少对历史总量的依赖 | 需要前后端协同设计，是长期收益最大的结构性优化 |
| 第三阶段 | 合并视图派生计算，并按实际收益决定是否引入增量索引和计数 | 进一步减少当日订单集合上的重复计算 | 在第二阶段完成后重新测量，确认收益足以覆盖维护成本再实施 |

第一阶段优先解决已确认且边界清晰的局部问题；第二阶段调整工作台的数据规模；第三阶段根据新的性能结果决定是否继续细化。增量重连同步列为后续候选方向，不作为前三阶段的前置条件。

下一轮门店基线采集前，先完成扩展实施方案中的 E01“完整结果文件导出”，解决用户反馈的长 JSON 无法通过剪贴板完整传递问题。该任务属于测量资料交付前置条件，不改变上述生产优化顺序。

## 4. 第一阶段：实时更新排序优化与基准补充

### 4.1 优化方案

在 `upsertOrders` 合并记录时，判断批次内是否包含新订单，或已有订单的时间线位置是否发生变化。判断应复用现有时间线比较逻辑，其排序依据为创建时间、显示编号及订单 ID。

若批次内所有已接受记录的时间线位置均未变化，则更新订单内容并复用原 `orderDisplayIds`；仅在新增订单或时间线位置变化时执行现有排序流程。肉、主食及出餐状态的普通变化不应单独导致完整时间线重排。

`upsertOrdersIfNewer` 的批次内最高版本去重和严格版本递增判断保持不变。已完成订单视图仍需在完成时间变化时维持正确顺序，不能将完整时间线的排序复用等同于所有视图均无需更新。

该优化消除无效排序及排序 ID 数组的重复分配，但仍保留不可变订单对象集合的复制成本，不能将整个更新过程认定为常数复杂度。

### 4.2 基准与验收

在既有本地单笔操作基准之外，增加以下独立场景：

1. 远端单笔订单状态更新，直接覆盖生产环境实际使用的批量合并方法。
2. 同一帧内多笔订单状态更新，覆盖批量去重与合并。
3. 新增订单或时间线位置变化，覆盖排序仍应执行的路径。

记录优化前后各五次测量结果及算术平均值，核对订单内容、ID 顺序和计数结果一致。回归验证应覆盖同版本、旧版本、批次内重复 ID、混合新增与更新，以及 HTTP 确认和实时事件先后到达的情况。

验收时应同时确认：普通进度变化复用排序 ID 数组；实际排序条件变化时结果正确；在相同基准配置下，实时状态更新的测量结果体现预期收益。性能变化应结合原始五次数据解释，不预设尚未经测量支持的降幅。

## 5. 第二阶段：按营业日限定工作台数据范围

### 5.1 优化方案

日常工作台仅加载并在内存中保存当前营业日所需的订单。历史订单继续由服务端保留，查询时按业务日期和分页条件获取，不再因进入工作台或连接恢复而自动下载全部历史数据。

后端应提供明确的业务日期范围查询能力或专用工作台快照能力，并在保持既有客户端兼容性的前提下确定接口方案。日期范围应采用明确的起止时间边界，并核对数据库查询与索引的匹配情况。

前端快照、实时事件接收和本地存储范围必须采用相同规则。实施前应明确：

- 当前营业日的定义及跨日未完成订单是否纳入工作台；保持现有业务语义，任何范围调整均应单独确认。
- 上海午夜切日、应用恢复前台和设备时间变化后的重新加载行为。
- 重连时快照与并发实时事件的合并，以及删除、清空事件的作用范围。
- 历史订单更新事件如何处理，避免其重新进入当日工作台集合。
- 工作区切换和历史查询数据的隔离，避免历史查询重新扩大工作台常驻集合。

不得仅在页面显示时过滤历史订单而继续将其全部下载到工作台 store；此类处理无法消除下载、内存和对象复制成本。

### 5.2 基准与验收

固定当日订单数为 130 单，将服务端历史总量依次扩展至 520、1820、10000 和 50000 单，分别测量工作台加载、日常操作和重连恢复。

验收应确认工作台返回和常驻客户端的订单数量由其业务范围决定，而非由全部历史总量决定；同时记录请求数量、传输字节数、加载耗时和客户端处理耗时。日常操作耗时应在历史规模扩大时保持相对稳定，具体波动范围应依据同一设备的基线测量确定。

功能验收应覆盖切日、后台恢复、重连、创建、删除、清空、失败回滚和并发更新，并核对历史查询与统计结果仍然完整。清空或删除的快照确认逻辑也需按新的数据范围验证，避免将范围外数据误判为已删除。

## 6. 第三阶段：共享派生结果与按需增量维护

### 6.1 优化方案

首先合并列表和顶部计数的重复遍历，使同一订单集合、业务日期及筛选条件下的派生结果可以复用。

在第二阶段完成后的测量结果仍显示派生计算占比较高时，再评估维护当日订单索引、完成状态分类及增量计数。进度变化未影响日期、分类或排序时，可复用相应结果；分类发生变化时，仅更新受影响的派生状态。

增量计数可以降低计数部分的计算成本，但不能自动消除订单对象集合复制、排序或 React 更新的全部开销。新增索引和计数必须统一处理创建、删除、清空、快照替换、回滚、工作区切换及业务日期变化，避免出现多份状态不一致。

### 6.2 实施条件与验收

该阶段以实际测量结果作为启动依据。如果按日限定数据后，工作台处理成本已满足门店设备的交互要求，可暂缓增量维护方案。

实施后应验证共享计算和增量结果与完整重算结果一致，并通过相同输入数据和事件序列进行对照。性能报告应区分派生计算的收益与整个订单更新的收益。

## 7. 后续候选方向：增量重连同步

在按日限定快照后，若重连恢复仍构成主要开销，可进一步评估基于服务端变更序号的增量同步。

该方案需要明确变更顺序、删除记录、事件保留期限及游标失效后的完整快照回退机制。仅依据订单更新时间查询，不能完整恢复删除和清空操作，因此不应直接替代现有快照校准流程。

此项涉及同步协议和服务端数据保留机制，实施复杂度较高，应在前述阶段完成并取得新的现场测量结果后再行立项。

## 8. 统一测量与交付要求

### 8.1 测量范围

测量应区分本地同步计算、界面更新、网络请求和服务端处理。纯计算基准用于比较算法与数据结构变化；首次加载和重连测试用于比较请求数量、数据传输及恢复过程；门店设备测试用于验证实际使用环境中的表现。

现有基准不包含真实网络、数据库和完整页面渲染，相关结果不得直接作为端到端响应时间。后续现场诊断可分别记录点击至界面反馈、请求往返，以及事件接收到界面更新的阶段耗时。

### 8.2 可复现要求

- 每个场景测量五次并取算术平均值，保留五次原始结果及内部预热、重复次数配置。
- 同组比较使用相同设备、运行时、数据分布、测量范围和基准协议，避免与构建或其他测试并行执行。
- 场景、数据规模或测量路径发生变化时，记录新的协议版本，并在新配置下重新采集优化前后结果；不覆盖既有基准记录。
- 记录代码版本、应用版本、设备和运行环境，分别解释开发电脑与门店设备的数据。
- 大规模测试应在设备空闲时分批执行；应用内测试应保留进度、取消及后台中止能力，不生成未完成轮次的正式平均值。

### 8.3 阶段交付物

每个实施阶段应交付代码变更、功能回归结果、五次基准原始数据及平均值、前后对比说明，以及剩余限制。前后端协同阶段还应交付接口与同步范围约定、兼容性方案和对应验证记录。

基准运行方式参见[订单工作台基准说明](../benchmarks/order-workspace/README.md)。
