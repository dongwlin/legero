# 性能基准测试与现场诊断扩展实施方案

编制日期：2026-10-15

文档状态：待实施方案

适用范围：Legero 前端、Capacitor Android 应用及其 Go／PostgreSQL 后端

## 1. 编制目的与执行范围

本方案规定性能测试与现场诊断能力的扩展范围、实施顺序、测量口径和交付要求，供后续会话独立执行。

现有部署环境为：后端与 PostgreSQL 运行于麒麟 710 平板的 Termux，通常连接 2 至 3 台 Android 客户端，每日约产生 130 笔订单。此前出现历史数据累积约四天后，实际操作设备提交“肉”“主食”“出餐”响应变慢的现象。已发布的修复降低了订单派生计算中的重复时区转换开销，后续仍需覆盖其他计算路径及完整业务流程。

本方案属于待实施规划。算法及数据范围的优化顺序见[订单工作台后续性能优化规划](order-performance-optimization-plan.md)，已完成的问题分析见[历史订单性能问题记录](order-toggle-performance.md)。测试能力扩展与生产优化分别记录：先建立目标路径的可比基线，再实施对应优化。

本文件中的阶段、场景规模及优先级为结合本项目提出的工程方案。官方资料提供测量方法和工具依据，不代表官方为本项目规定了相同参数或验收阈值。

## 2. 方法依据与总体原则

采用“可重复的场景基准、实际业务交互测量、按需性能分析、现场诊断记录”相结合的方法。受控测试用于复现和版本比较，实际设备测量用于验证用户体验，性能时间线用于识别未知耗时来源。Google 官方将实验室测量和实际用户测量视为相互补充的证据。[参考：用户感知性能指标](https://web.dev/articles/user-centric-performance-metrics)

- 按业务计算、React 渲染、浏览器呈现、网络、服务端及设备资源分别计量，明确起止边界。
- 将历史数据规模、当日订单规模、批量更新量、并发客户端数和连续运行时间作为独立变量。
- 调用生产代码路径，不复制简化算法替代被测实现；同时验证业务结果。
- 可重复基准使用隔离数据；现场记录仅观察正常业务操作，不自动修改真实订单。
- 每个基准场景保留五轮原始结果及算术平均值；持续运行和现场采样另列统计口径。
- 门店实际 Android 应用结果单独报告，开发电脑及桌面浏览器结果用于开发回归。
- 失败、取消、超时和能力缺失明确表示，不生成虚假的成功平均值。

### 3.1 已有实现

| 能力 | 当前入口 |
| --- | --- |
| 共享计算工作负载 | [`src/services/orderBenchmark.ts`](../src/services/orderBenchmark.ts)，调用真实状态函数、隔离的 Zustand store 及列表／计数派生函数 |

| 应用内基准 | [`src/views/Settings/Benchmark/index.tsx`](../src/views/Settings/Benchmark/index.tsx)，路由 `/settings/benchmark`，支持进度、取消及结果复制 |
| 实时连接诊断 | [`src/services/realtimeDiagnostics.ts`](../src/services/realtimeDiagnostics.ts)，记录连接、重连、恢复、快照校准及有限条状态变化 |
| 诊断页面 | [`src/views/Settings/Diagnostics/index.tsx`](../src/views/Settings/Diagnostics/index.tsx)，展示实时诊断快照 |
| 已有运行说明 | [`benchmarks/order-workspace/README.md`](../benchmarks/order-workspace/README.md)，说明协议及已保存结果的适用范围 |

当前计算协议为版本 1，包含 130、520、1820 笔总订单，每个场景固定 130 笔当日订单。一次记录操作包含乐观状态写入、视图派生、模拟服务端确认写入及再次派生。

每轮中，每个场景的每种动作先执行两次预热，再执行五次记录操作；轮值为五次操作的平均值，最终结果为五个轮值的算术平均。CLI 使用五个顺序启动的独立 Node 进程；应用内使用同一浏览器进程中的五个隔离 store。现有 JSON 保存五个轮值，不保存轮内逐次操作原值。现有视图数量断言处于动作计时区间内。

### 3.2 尚未覆盖的范围

当前基准不包含真实 WebSocket 接收与帧内批处理、完整乐观请求管理、真实 HTTP／数据库、React 渲染、DOM 布局与绘制、磁盘持久化及重复点击保护。数据生成、初始注入及初次视图派生也位于现有计时范围之外。

既有实时诊断主要保存最近一次耗时、累计次数和有限状态记录，不能直接充当五轮基准的逐样本采集器。复用时应注意：

- 连接耗时从创建实时 session 前开始，到收到 ready 为止，不包含此前的认证刷新。
- 恢复耗时结束于 online 状态，不代表快照校准及订单界面已经可用。
- 快照校准耗时包含该同步流程内的网络、缓冲事件处理及 store 更新，不包含 React 渲染和浏览器呈现。

实施前重新核对上述代码与边界；若仓库已有后续改动，应更新现状说明，避免重复建设。

## 4. 指标定义与计时规则

### 4.1 业务指标

下列名称为建议标识，实际字段应在实施时随结果协议确定并保持稳定。

| 指标 | 起止边界与用途 |
| --- | --- |
| `storeCommitMs` | 进入目标 store 方法至方法完成，识别复制、版本检查、排序等同步计算成本 |
| `viewDerivationMs` | 开始派生列表／计数至结果生成，区分状态写入与派生计算 |
| `interactionDurationMs` | 使用 Event Timing 测得输入至相关下一帧呈现的交互时长；仅在能力可用且事件匹配可靠时提供 |
| `businessFeedbackMs` | 原始输入至目标业务状态实际呈现；需要可验证的呈现测量方法，否则分别报告 state／commit 阶段及限制 |
| `requestRoundTripMs` | 客户端发起请求至响应正文读取完成；解码及状态合并另列阶段 |
| `serverAckMs` | 本地接受业务操作至收到并解析有效成功响应；失败和超时单列 |
| `syncReceiveToStateMs` | 本设备收到实时事件至相关状态合并完成，包含批处理等待 |
| `syncReceiveToCommitMs` | 本设备收到实时事件至目标 React 更新提交；未测量呈现时不标记为画面已显示 |
| `workspaceReadyMs` | 开始进入／恢复工作台至快照和缓冲事件校准完成、必要交互可用，另列 online 与首个画面时间 |
| `reactRenderMs` | React Profiler 的 `actualDuration`，表示指定子树的渲染耗时，不代表浏览器布局和绘制耗时 |

自定义阶段使用 W3C User Timing 的 `performance.mark()` 与 `performance.measure()`；完成聚合后清理条目，限制缓冲区增长。[参考：User Timing](https://www.w3.org/TR/user-timing/)

### 4.2 呈现与跨设备边界

INP 衡量交互响应，不覆盖所有异步请求完成后的业务结果，也不衡量滚动流畅度。单次 Event Timing 事件时长不得直接命名为整个页面的 INP。[参考：INP](https://web.dev/articles/inp)

状态写入结束、React 提交、`requestAnimationFrame` 回调或连续两次该回调，均不能单独证明目标状态已经呈现在屏幕上。近似测量应标注 `state`、`commit` 或 `approximation`；实际呈现结合受支持的浏览器指标、性能轨迹及画面验证。原始输入时间无法取得时，处理函数入口起算的结果应注明其未包含输入排队时间。

同一设备内的持续时间使用同一上下文的单调时钟，不使用业务 `createdAt`／`updatedAt` 计时。多设备同步以测试关联标识串联记录，不直接相减不同设备的系统时间或 `performance.now()`。完整的“设备 A 点击至设备 B 显示”耗时应采用统一外部计时观察，或明确时钟校准与误差；缺少条件时只报告各设备内部阶段及确认往返耗时。

## 6. 分阶段实施与验收

### 6.1 第一阶段：计算与实时更新基准

覆盖 C01 至 C05，优先新增 `upsertOrdersIfNewer` 实际使用的批量路径。检查 [`src/store/order.ts`](../src/store/order.ts)、[`src/hooks/useOrderWorkspaceSync.ts`](../src/hooks/useOrderWorkspaceSync.ts)、[`src/services/orderRealtime.ts`](../src/services/orderRealtime.ts) 及现有基准。未接入帧内排队或 WebSocket 解码时明确列为排除项，不将直接调用 store 表述为完整实时链路测量。

保留版本 1 结果；新增场景、参数或计时范围时发布新协议，重新采集可比基线。新协议保存逐次操作样本，并明确正确性断言是否计入耗时。

交付与验收：CLI 与应用内可运行共享场景；保留五轮数据；覆盖真实方法并核对结果；列明包含／排除项；取消、失败及后台中止正确。随后再按优化规划处理无效排序等问题，在相同协议下比较前后结果。

### 6.2 第二阶段：实际交互与门店记录入口

覆盖 U01、U02，建立有容量和时限限制的记录器。复用现有设置页与诊断出口，清楚区分隔离基准、用户主动开始的实际操作记录，以及开发排查使用的详细分析。

对订单列表、统计及表单按需启用 React Profiler。生产分析需要专门的 profiling 构建，且本身存在开销；记录是否开启分析，普通发布构建与分析构建分别比较。[参考：React Profiler](https://react.dev/reference/react/Profiler)

逐项检测 Event Timing、Long Tasks、Long Animation Frames 及元数据能力；缺失记为 unavailable／空值并注明原因，不填 0，不根据空记录推断不存在卡顿。Long Animation Frames 自 Chrome 123 提供，记录超过 50 毫秒的长动画帧，不能替代所有帧或滚动测量。[参考：Long Animation Frames](https://developer.chrome.com/docs/web-platform/long-animation-frames)

Event Timing 记录采集阈值 `durationThreshold`，按可靠且非零的 `interactionId` 归并相关事件，无法分组时注明限制。区分“能力不可用”“未达到报告阈值”和“未发生目标交互”，不能仅对已报告的慢事件求平均后声称得到全部交互的平均值。[参考：Event Timing](https://www.w3.org/TR/event-timing/)

交付与验收：可开始、停止、取消及导出；每项指标有边界与能力状态；使用受控慢任务／慢渲染验证采集有效；条数与时长有上限；旧 WebView 缺失能力时业务和诊断页仍可用；记录功能开关的额外开销。

### 6.3 第三阶段：加载、同步与多设备流程

覆盖 S01 至 S03，复用实时诊断定义，补充逐次样本和业务可用阶段。分别记录请求、响应体读取、转换、快照合并、缓冲事件回放和界面更新，避免将重叠阶段相加形成错误总耗时。

桌面自动化复用现有浏览器测试能力；真实 Android 应用另行验证。采用 Lighthouse 时，可使用 User Flows 的 timespan 模式分析交互流程；该模式不提供统一性能总分。[参考：Lighthouse User Flows](https://github.com/GoogleChrome/lighthouse/blob/main/docs/user-flows.md)

交付与验收：1 至 3 客户端下可重复执行；每轮初始状态、故障与完成条件明确；ready、校准完成及界面可用独立记录；并发、删除、清空和回滚结果一致；跨设备关联不依赖未经校准的时钟相减。

### 6.4 第四阶段：长期运行与资源趋势

覆盖 L01，分别测试历史规模增长和固定规模长时运行。先建立轻量循环，再扩展 2 小时及按需的 8 小时配置；场景与负载配置分离，复用业务操作序列。参考 k6 的平均负载、突发及 soak 测试组织方法，工具选型不要求引入云服务。[参考：持续性能测试](https://grafana.com/docs/k6/latest/testing-guides/automated-performance-testing/)

交付与验收：保存时间序列、操作次数、失败数及阶段窗口统计；取消与资源释放正确；区分业务数据保留、垃圾回收波动和疑似泄漏。内存接口缺失时使用受支持的调试工具或系统观测，并标明来源；JS heap 不等同于 Android 进程总内存，单次上升不直接认定为泄漏。

### 6.5 第五阶段：服务端与系统诊断

覆盖 A01。后端以分阶段计时或 `Server-Timing` 提供服务处理及数据库耗时，通过请求关联标识与前端记录对应；跨源读取时检查所需响应头。Go 热点按需使用 pprof。监测维度参考 Google SRE 的延迟、流量、错误和饱和度。[参考：Server Timing](https://www.w3.org/TR/server-timing/)、[Go Diagnostics](https://go.dev/doc/diagnostics)、[Google SRE](https://sre.google/sre-book/monitoring-distributed-systems/)

进一步排查时，通过调试能力已开启的实际 APK 连接 Chrome DevTools，录制 JavaScript、渲染与网络时间线。资源竞争问题使用 Perfetto 查看进程调度及 CPU 频率；针对本项目，可据此分析 WebView 与 Termux 后端／数据库的资源竞争，结论以实际轨迹为准。[参考：WebView 调试](https://developer.chrome.com/docs/devtools/remote-debugging/webviews)、[Perfetto 系统追踪](https://perfetto.dev/docs/getting-started/system-tracing)

Android Macrobenchmark 可作为后续启动及整机交互自动化工具。Activity 首帧不代表 React 工作台数据已加载；JavaScript 热点仍结合 WebView 工具分析。[参考：Macrobenchmark 指标](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-metrics)

交付与验收：至少一个慢请求能关联客户端、服务端及数据库阶段；记录工具和采集开销；旧 Android 限制有替代路径或明确缺项。若前期证据已指向服务端或系统瓶颈，可将本阶段提前并说明依据。

## 7. 数据隔离、结果协议与统计要求

### 7.1 数据隔离与执行控制

计算及界面夹具使用独立 store、内存 storage 和隔离数据／事件适配器，不借生产 singleton 的 mutation、订阅或持久化写入测试数据。网络基准使用明确隔离的测试环境与工作区；清理只针对本轮夹具，不调用门店真实数据的全量清空。现场记录观察用户正常操作，不自动注入业务请求。

分批执行并提供进度、取消和超时。隔离基准退后台或离页时中止；专门的前后台恢复场景及现场记录则按显式生命周期策略结束或标记阶段，不将后台节流误判为前台计算回归。中止后释放连接、监听器、定时器和测试数据。

### 7.2 结果结构

扩展结果至少包含：

- 协议与结构版本、场景编号、代码提交、相关源码摘要及未提交改动状态。
- 应用版本、构建模式、运行时、设备型号、Android／WebView 版本及采集能力；缺失字段注明原因。
- 数据种子、业务日期、订单分布、批次数量、并发数、冷／热启动、预热次数、每轮操作次数及计时边界。
- 五轮逐项数据、逐次操作样本、平均值、最小值、最大值及样本数；分析波动时记录标准差。
- 失败／取消／超时状态与次数、正确性结果、排除项及诊断采集开关。
- 长时与现场记录的时限、容量、实际保留数量、丢弃／聚合数量及保留策略，例如最近窗口、抽样或在线聚合。

诊断导出以固定指标、计数及受控关联标识为主，不包含 token、session ticket、手机号、订单正文或完整请求／响应。关联标识按一次测试或记录会话生成，不复用业务内容。默认本地记录与主动导出，不自动上传。

### 7.3 五轮与尾部统计

维持现有“先求每轮操作均值，再对五轮等权求均值”的口径，每轮有效记录次数相同。其他聚合方式单独定义，不与既有结果直接混合比较。

任一轮失败、取消或中断时保留部分记录和状态，不生成完整五轮的正式平均值，不静默丢弃异常轮。预热与正式样本分开；单轮最大操作耗时与五个轮值中的最大值分别命名。

五个轮值用于基准比较，不足以稳定描述 P95／P99。尾部统计用于样本充分的长时测试或现场记录，报告样本数、时间窗口及计算方法；不得将“五个均值的 P95”当作单次操作尾延迟。长时场景也定义五轮计划及轮长；未完成五轮时仅交付已完成记录，不宣称具备五轮均值。

有界记录器仅保留部分样本时，分位数明确对应保留窗口、抽样样本或支持该统计的聚合结果，不将其表述为整个运行周期的完整样本统计。

### 7.4 比较与门槛

同组比较使用相同设备、构建模式、运行时、数据分布、协议及计时范围，不与构建、其他基准或重负载任务并行。记录网络及可观测的充电、温度等环境条件；额外轨迹采集与常规测量分开说明。

先建立基线和波动范围，再依据门店可接受的响应制定指标预算与回归门槛，不预设未经验证的统一毫秒阈值或优化百分比。性能比较前先通过正确性校验，避免因跳过必要工作获得表面收益。

## 8. 跨会话执行与交付约定

### 8.1 每个实施会话的顺序

1. 阅读所在仓库的 `AGENTS.md`、`AGENTS.local.md`、技能规则及本方案，核对分支、未提交改动和当前实现；前后端协作时分别检查两仓库要求，不复制本机凭据。
2. 明确本次阶段、场景编号、被测路径、起止边界及排除项，检查已有后续实现，避免重复建设。
3. 实现并校验测量能力，形成新场景五轮基线；保留既有记录。若同时优化生产代码，先保存优化前基线。
4. 实施变更，验证业务正确性、协议、取消和兼容性；涉及界面时验证实际交互，涉及后端时增加对应集成验证。
5. 修改生产性能路径后在同一配置下采集优化后五轮结果并比较；仅增加覆盖时说明新基线，不宣称产生业务性能收益。
6. 更新场景说明、协议、报告和阶段状态，检查导出内容，按独立可审阅的单元提交。
